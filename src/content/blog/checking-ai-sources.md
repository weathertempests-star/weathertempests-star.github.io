在[上一張創作委託](/blog/learning-in-public/)裡，我們替網站寫了一段 RSS 訂閱介紹。現在把焦點移到它的事實：如果草稿附上官方文件的連結，要怎麼判斷這個連結真的支持旁邊的文字？

先看一段刻意混入錯誤的練習材料。這段文字為本篇構造，不是某次模型的真實回應：

> RSS 使用 XML 格式，所有訂閱都會即時推送全文。只要設定 `ttl=60`，網站就會每小時發布一次新文章。這些功能都寫在 RSS 2.0 規格裡。

它把格式、內容、更新方式和發文頻率塞進了三句話。即使結尾連到真實文件，也要把每一件事分開檢查。

## 第一個問題：連結通往什麼？

先打開來源，確認是誰發布、談的是哪個版本，以及哪一段與這次問題有關。搜尋結果的摘要可以幫忙找路，正式採用一個說法之前，還是需要看它所在的原文。

本例使用 RSS Advisory Board 提供的 [RSS 2.0 規格](https://www.rssboard.org/rss-specification)。它適合回答「這個格式如何定義欄位」，卻不能直接回答某個閱讀器現在怎麼呈現內容。後者需要該產品的文件或實際檢查。

如果來源無法開啟，我會先留下尚待核對的標記，再找可確認的原始出處。找到一個標題相似的頁面時，也要重新閱讀，確認它確實支持原本要發布的句子。

## 第二個問題：它支持哪一句話？

把練習材料拆開，可以得到四個獨立主張：

| 草稿中的主張            | 查核位置與判斷                                      |
| ----------------------- | --------------------------------------------------- |
| RSS 使用 XML 格式       | 規格的格式介紹支持這個說法。                        |
| 所有訂閱都即時推送      | 草稿沒有提供足以支持「所有」與「即時」的依據。      |
| 訂閱一定顯示全文        | `item` 說明允許摘要，也允許完整內容；不能保證全文。 |
| `ttl=60` 決定每小時發文 | `ttl` 說明的是快取時間，不能推導出發文排程。        |

後兩項的依據，可以直接在規格的 `item` 與 `ttl` 小節核對。`ttl` 以分鐘表示從來源重新取得資料前可快取的時間；它也不是要求作者定時寫一篇文章的指令。[RSS 2.0 規格](https://www.rssboard.org/rss-specification)

其中第二項要特別留意：查不到「所有訂閱都即時推送」的根據，就先移除這個保證。不能因此把句子反過來寫成「RSS 絕不會收到更新通知」；那同樣多做了一個原文沒有支持的判斷。

## 第三個問題：條件有沒有被改掉？

查核時，我會圈出「所有」「一定」「只要」這類擴大範圍的詞，再回到原文找它的條件。原文允許某個功能，與每個服務都會實作，是兩個需要分別確認的命題。

同樣的問題也出現在版本、對象與時間上。一份描述 RSS 2.0 的文件，可以支持這個版本的格式定義；一句關於特定工具的操作說明，則要對應那個工具。把兩者合成「各種訂閱都一樣」，中間還缺了證據。

引用放得越靠近主張，讀者越容易看出它負責證明哪一部分。一整段包含數個判斷時，我會拆成較短的句子，讓支持範圍更清楚。

## 把句子改寫到證據支持的範圍

練習材料可以改成：

> RSS 是一種使用 XML 的內容聯播格式。訂閱項目可以提供摘要，也可以包含完整內容。`ttl` 描述快取時間，不能用來判定網站的發文頻率。

這段適合說明規格。如果要放回首頁的小卡片，還要再依讀者用途縮短，保留「把網址加入閱讀器」這個操作。**查核完成與文案適用，是兩項各自需要確認的工作。**

對於不影響操作的細節，可以移到延伸閱讀。對於無法確認、又會影響讀者理解的保證，就應先刪除，等有足夠依據再補上。

## 留下一筆可以重查的紀錄

發布前，我會替關鍵事實保留三項資訊：採用的句子、直接支持它的來源，以及適用範圍。本例可寫成「RSS 2.0 的項目可以是摘要或完整內容；來源為 `item` 小節；不保證特定閱讀器的顯示方式」。

這筆紀錄讓後續修訂能回到當時的依據。若作品改成介紹某個閱讀器，就知道還要補哪一種資料，而不是沿用一句看起來熟悉的結論。

文字的查核可以逐句做。遇到可執行的交付物，則可以再把預期寫成測試；[梯度下降的小實驗](/notes/gradient-descent/)示範了如何從一個手算答案，走到能重做的程式檢查。
