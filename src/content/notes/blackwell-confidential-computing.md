大型語言模型（LLM）在雲端推論時，提示詞與模型權重會經過主機和 GPU；生成的內容也會從 GPU 回到主機。  
可信執行環境（TEE）要保護這些資料，卻讓每次跨越保護邊界都有可能變慢。  
這篇 [Blackwell 機密運算效能研究](https://arxiv.org/html/2608.26575v2)提供一個有用的拆解方法：看主機提交工作、取回結果，以及多張 GPU 交換資料，各自讓推論付出多少時間。

## 同一台機器，為何會有不同答案

作者在同一台配有 Intel Xeon、NVIDIA B200 的主機上，比較開啟與關閉機密模式的成對實驗。  
開啟時，Intel TDX 保護虛擬機記憶體，Blackwell 的機密模式把保護延伸到 GPU，並加密 CPU 與 GPU 之間的 PCIe、GPU 之間的 NVLink 傳輸。  
兩次執行使用相同磁碟、模型與 GPU，因此同一組配置的吞吐量差異，較能用來觀察機密模式的成本。  
論文也使用不同模型和服務框架；跨組數字只能說明可能的機制，不能直接當成只改動一個參數的實驗。（[論文第 2、3 節／表 1](https://arxiv.org/html/2608.26575v2)）

吞吐量指一段時間能產生多少輸出 token；token 是模型處理文字時使用的單位，可以是字、詞或詞的一部分。  
一次請求先處理輸入，再逐步產生 token。  
這兩段工作中，GPU 計算、主機控制及 GPU 間傳輸所占的比例不同，因此機密模式沒有一個適用所有推論的固定成本。

## 每次由主機提交工作，都要跨過加密控制通道

GPU 核心程式（kernel）是交給 GPU 執行的一項運算工作。  
主機每提交一項 kernel，就要透過控制通道通知 GPU；在機密模式下，這條通道也受加密保護。  
作者的單卡細部量測顯示，一次提交約多花 **12 微秒**，單純等待 GPU 完成工作的額外時間則接近零。  
差別看似很小，但模型每產生一個 token，可能連續提交上百項 GPU 工作，固定成本會反覆累積。（[論文第 5.2 節／表 5](https://arxiv.org/html/2608.26575v2)）

CUDA graph 的做法是把一串 GPU 工作預先記成可重播的圖，之後由主機一次啟動，而不必每一步重新提交。  
論文的合成實驗把整個產生 token 的步驟記成一張圖，觀察到大部分提交成本消失。  
這是用來確認原因的理想化設定：真實服務框架可能把圖分段，每段仍要主機啟動。  
所以判斷機密推論速度時，光知道「用了 CUDA graph」還不夠，還得知道每步剩下多少次主機提交。（[論文第 5.2 節／表 6、7](https://arxiv.org/html/2608.26575v2)）

## 回傳一個結果，可能讓下一步等在原地

產生 token 後，服務框架要把取樣結果從 GPU 讀回主機，才能安排接下來的工作。  
正常情況下，框架可以讓資料回傳與下一步 GPU 運算重疊進行；兩件事同時前進，回傳的等待時間便不會全部落在關鍵路徑上。  
論文測試的未修補 SGLang，在機密模式下卻將這段讀回變成同步操作，排程器必須等它完成，GPU 因而空轉。  
Qwen3-8B 單卡測試在不同並行請求量下，吞吐量下降約 **34–39%**。  
這個大幅下降指向「重疊被破壞」：等待造成的損失，遠超過單次資料加密本身。（[論文第 6.2 節／表 12](https://arxiv.org/html/2608.26575v2)）

作者把讀回工作移到另一個執行緒，並加入其他相容機密模式的框架修補；修補後的另一組單卡模型，主要測試點的差距已很小。  
由於前後使用不同模型，這些結果適合說明阻塞機制及可行的修補方向，不能視為同一負載只改一項設定的前後對照。（[論文第 6.4 節／表 14、第9 節](https://arxiv.org/html/2608.26575v2)）

## 多張 GPU 的成本跟著通訊走

把模型分到多張 GPU 時，各張卡需要交換中間結果。  
如果採張量並行，這種交換會在模型的許多層反覆發生，資料也要經過加密的 NVLink。  
減少主機提交次數不能消除這筆傳輸；整體損失取決於 GPU 間通訊在一次請求中占了多少時間。  
在論文的張量並行配置中，輸入處理較依賴跨卡交換；輸出產生較長時，前段傳輸的成本可分攤到更多 token 上。（[論文第 5.3、7.1 節](https://arxiv.org/html/2608.26575v2)）

在修補後的 SGLang 上，作者以 MiniMax-M2.7、輸入 1024 token、輸出 2048 token、同時處理 32 個請求測試。  
八卡張量並行的重複量測顯示約 **2.8–3.6%** 吞吐量損失；縮成四卡張量並行時約 **1.5%**。  
這裡減少的是每次交換時的參與者與加密流量。  
同一研究也觀察到短輸出請求的成本明顯較高，足以提醒我們：這幾個低個位數結果描述的是指定模型、長度與並行配置，並非 Blackwell 所有推論的上限。（[論文第 7.5 節](https://arxiv.org/html/2608.26575v2)）

讀完這篇，我會先檢查服務框架有沒有保住運算與資料回傳的重疊、每步還有多少主機提交，再看模型切分是否製造了不必要的跨卡交換。  
約 1–3% 可以作為這組 B200、TDX、已修補框架及偏重輸出生成的配置下的量測參考，實際重複測試也有略高於 3% 的結果；訓練、其他模型和不同部署方式仍須分開估算。  
論文只測單一實體主機，也沒有量測遠端證明、啟動和跨機傳輸的整體成本，更沒有驗證系統對特定攻擊者是否安全。  
這些界線和吞吐量數字一樣，都是解讀結果時不可省略的條件。（[論文第 1.3、8 節](https://arxiv.org/html/2608.26575v2)）
